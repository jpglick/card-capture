# Card Capture v2.2 Architecture Specification: Normalization, Fusion & Advanced Evidence

**Project:** Sports Trading Card Image Extraction from Video  
**Target Audience:** Implementation LLM / Coding Agent  
**Status:** Approved Architecture Specification (Extension of v2.1)
**Constraint:** Do NOT implement any grading, defect scoring, or pricing lookups.

## 1. Architectural Mandate

With the v2.1 pipeline successfully grouping frames and applying initial homography, this phase implements the final image polish, multi-frame enhancement, and evidence-collection features. 

The primary goals are:
1. **Precision Normalization:** Enforce strict aspect ratios, exact pixel dimensions, and tight cropping to ensure absolute consistency across all extracted images.
2. **Diverse Lighting Collection:** Intelligently select a subset of views that capture the card under different lighting conditions.
3. **Multi-Frame Fusion:** Mathematically combine multiple views to create a single, glare-free, high-resolution composite image.
4. **Diagnostic Telemetry:** Store foundational metadata (glare masks, sharpness maps) for future downstream systems.
5. **UI Modernization:** Upgrade the review UI to support multi-view instances.

## 2. Pipeline Extensions (Append to v2.1 Pipeline)

### Stage 7: Precision Normalization & Cropping
* **Objective:** Ensure every single `CardView` conforms to an identical pixel grid and removes any residual background bleed from slight corner-detection inaccuracies.
* **Action:**
    1. **Strict Aspect Ratio:** Define a global target pixel dimension based on standard trading cards (e.g., 2.5 x 3.5 inches translates to `750x1050` pixels at 300 DPI). 
    2. **Overscan Crop (Safety Margin):** Apply a tiny, programmable "inner crop" (e.g., 1-2%) to the homography-warped image to trim any remaining background pixels along the outer edges.
    3. **Resampling:** Resize the cropped image to the exact `750x1050` target dimension using high-quality Lanczos or Bicubic interpolation (e.g., `cv2.INTER_LANCZOS4`).
* **Output:** The `CardView` is now a perfectly uniform, cleanly edged array ready for mathematical comparison and fusion.

### Stage 8: Lighting-Diverse Evidence Selection
* **Objective:** Instead of just keeping the "sharpest" view, keep a representative set of views based on how light interacts with the card (crucial for foil/refractor identification later).
* **Tool:** OpenCV (`cv2.cvtColor`, `cv2.calcHist`, `cv2.threshold`)
* **Action:** 1. Convert each normalized `CardView` to HSV or LAB color space.
    2. Create a "Glare Mask" by thresholding for high brightness (V/L channel) and low saturation (S/A/B channels).
    3. Calculate the spatial center of mass for the glare mask (e.g., is the glare on the top, bottom, left, or right of the card?).
* **Output:** Select 3 to 4 `CardViews` per `CardInstance` that have the highest sharpness scores *while ensuring the glare is located in different physical regions* of the card. 

### Stage 9: Multi-Frame Fusion (The "Clean" Composite)
* **Objective:** Generate a single, visually perfect "Display Image" by removing moving glare and reflections.
* **Tool:** `numpy` pixel operations and `cv2.alignMTB` (or simple median blending).
* **Action:**
    1. Take the exact `750x1050` `CardViews` selected in Stage 8. (Because they went through Stage 7 normalization, they are mathematically aligned pixel-for-pixel).
    2. Because glare is strictly additive (it makes pixels artificially brighter), apply a **Minimum or Median Pixel Blend** across the stack of images. 
    3. *Logic:* For every `(x, y)` pixel coordinate, look at the values across all selected views. Taking the median (or a heavily weighted minimum) will naturally eliminate the white glare spots, resulting in a clean composite.
* **Output:** Save this new generated image as the `Fused_Canonical_View`.

### Stage 10: Diagnostic Metadata Storage
* **Objective:** Save the mathematical artifacts generated during processing so future ML models (when implemented) don't have to recalculate them.
* **Action:** Compress and save the following as lightweight arrays (e.g., `.npz` or `.parquet`) alongside the SQLite database entry for the `CardInstance`:
    * The computed Glare Masks (binary arrays).
    * Laplacian sharpness heatmaps.
    * The exact crop/normalization offsets used in Stage 7.

### Stage 11: Multi-View Review UI Refactor
* **Objective:** Update the Flask/FastAPI web interface to reflect the new data structure.
* **Action:** 1. Change the main feed to display the `Fused_Canonical_View` by default.
    2. Add a "Filmstrip" or "Carousel" component below each main image, allowing the user to click through the individual Lighting-Diverse `CardViews`.
    3. Add a visual indicator (e.g., an icon) showing how many frames were fused to create the composite.

## 3. Implementation Directives for LLM Agent

When executing this specification, adhere to these rules:

1. **Isolation of Fusion:** The fusion process (Stage 9) must be non-destructive. Never overwrite a raw `CardView` with a fused image. The fused image is a *derived artifact*.
2. **Strict Dimensions:** Treat the target resolution defined in Stage 7 as a global constant. Assert that all arrays passed into Stage 9 have the exact same shape.
3. **Performance Constraints:** Pixel-wise operations across image stacks can be memory intensive. Ensure `numpy` arrays are handled efficiently (e.g., cast to `uint8` where possible) and avoid deep-copying arrays in memory unnecessarily.
4. **No Grading Logic:** You are strictly forbidden from adding any code that attempts to score the condition, centering, corners, or surface of the card based on the gathered evidence. Your only job is to *collect, normalize, and fuse* the evidence.
5. **Step-by-Step Execution:** Do not build all stages at once. Begin with Stage 7 (Normalization & Cropping) and write shape-assertion tests for it before attempting the lighting selection and fusion logic.
